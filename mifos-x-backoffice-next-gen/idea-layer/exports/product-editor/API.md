## Error Handling

All endpoints follow standard error mapping:
- 401 -> Auth error (redirect to signin)
- 403 -> NoAuthorization -> `permission-capability-engine` re-resolves `READ_LOANPRODUCT` / `CREATE_LOANPRODUCT` / `UPDATE_LOANPRODUCT`
- 404 -> NotFound error
- 422 -> Validation error
- 500 -> Server error (retryable)

Notes:
- `get_product` + `get_product_template` are reads — CACHE_FIRST_SWR through Store5: every field, bound, and option comes from the template so the form always matches the server's product schema and drafts offline. (Savings products use `/v1/savingsproducts/{id}`, referenced in `docs.yaml#summary` but not yet declared as a separate `api.yaml` endpoint.)
- `save_product` is enqueued to the durable `draft_outbox` with a UUIDv4 idempotency key and replayed via `POST /v1/batches` (exactly-once). Per `data-flow.yaml`, product/config edits are **online-only** (not silently drained on reconnect like a field transaction) — an offline attempt is blocked with a connect banner, and a rejected replay surfaces in the needs-attention inbox rather than being silently dropped. `PUT` edits an existing product (`UPDATE_LOANPRODUCT`); `POST /v1/loanproducts` creates a new one (`CREATE_LOANPRODUCT`).
