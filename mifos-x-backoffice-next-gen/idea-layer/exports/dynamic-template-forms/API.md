## Error Handling

All endpoints follow standard error mapping:
- 401 -> Auth error (redirect to signin)
- 403 -> NoAuthorization -> permission-capability-engine drift refresh + re-resolve (datatable read requires READ_DATATABLE)
- 400 -> Validation error -> server errors[] mapped back onto the offending field by parameterName
- 409 -> Optimistic-lock conflict -> error state, offending field surfaced
- 500 -> Server error (retryable; error state + Retry)

Notes:
- `get_entity_template` + `get_datatables` are reads — CACHE_FIRST_SWR: the cached schema renders instantly and a background revalidate refreshes it, so a back-office config change appears on the next sync with no app release.
- `submit_entity_command` is enqueued through the offline outbox with a durable UUIDv4 Idempotency-Key and replayed as an all-or-nothing batch (`POST /v1/batches`) — exactly-once, zero double-post.
- The engine is entity-agnostic: the concrete `{ACTION}_{ENTITY}` permission (CREATE_CLIENT, APPROVE_LOAN, ...) is inherited from the caller screen; a `commandId` without a `resourceId` = submitted-for-approval (maker-checker queued).
