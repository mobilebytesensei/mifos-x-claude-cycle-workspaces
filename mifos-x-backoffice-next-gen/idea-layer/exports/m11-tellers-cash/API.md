## Error Handling

All endpoints follow standard error mapping:
- 401 -> Auth error (redirect to signin)
- 403 -> NoAuthorization -> permission-capability-engine drift refresh + re-resolve (not a crash)
- 404 -> NotFound error
- 409 -> Optimistic-lock / conflict (e.g. settle > allocated) -> Review failed -> needs-attention-inbox
- 422 -> Validation error (Fineract command rejected)
- 500 -> Server error (retryable; error state + Retry)

Notes:
- `list_*` + `get_*_template` are reads served CACHE_FIRST_SWR over Room (`tellers_cash`, `cached_templates`) so the teller list, cash position, cashier roster and ledger render offline; every call sends the global `Fineract-Platform-TenantId` header.
- `create_teller` / `update_teller` / `assign_cashier` / `allocate_cash` / `settle_cash` are enqueued through the durable outbox (`draft_outbox`) with an idempotency key and replayed exactly-once via `POST /v1/batches` — a cash movement never double-moves, even across an app kill mid-submit.
- `allocate_cash` / `settle_cash` are money-sensitive: a client-side guard blocks `insufficient_vault_cash` / `settle_exceeds_allocated` before enqueue; the server stays the final authority.
- Commands are maker-checker aware: a `commandId` without a `resourceId` = submitted-for-approval (not applied optimistically) → M15 (Approvals).
