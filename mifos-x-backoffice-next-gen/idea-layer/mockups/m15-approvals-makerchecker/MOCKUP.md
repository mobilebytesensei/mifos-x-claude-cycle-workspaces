## Screen Intent

The full maker-checker approvals module (the checker-inbox drill-in is its dashboard-scoped view). Loads the self-scoped queue (`GET /v1/makercheckers`), **grouped** under entity/action/maker headers with per-group counts. Each row opens a payload inspect panel; **Approve / Reject / Delete** render only when the checker `canCheck(entry.action, entry.entity)` (CHECKER_SUPER_USER or `{ACTION}_{ENTITY}_CHECKER`). A multi-select bar enables **bulk-approve**. Decisions enqueue to the offline outbox (exactly-once via `POST /v1/batches`); a resolving row is locked so a command can never be double-approved.

## App Shell (resolved from `app-shell.yaml`)

- **Top app bar** — small M3, `surface`, title "Approvals", menu/back leading.
- **Bottom navigation** — visible as a module root. **Offline banner** — decisions queue offline; a resolving row shows a queued indicator.

### State: `submitting` — decision in flight
An approve/reject/delete/bulk-approve enqueues to the outbox (idempotency key, exactly-once via batches); the affected row(s) show a queued indicator and lock from re-selection; the rest of the queue stays interactive.

## Accessibility & Density Notes

- Approve/Reject/Delete appear only on `canCheck`-gated rows; Reject/Delete are destructive + confirm.
- A resolving row is locked from re-selection — a command can never be double-approved.
- Bulk-approve operates only over already-canCheck-gated selections.
- Cross-link to `needs-attention-inbox` is read-only — M15 never mutates that feed.
