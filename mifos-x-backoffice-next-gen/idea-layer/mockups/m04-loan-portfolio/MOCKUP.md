## Screen Intent

The loan portfolio module: origination · servicing · delinquency · reschedule. An office-scoped paged loan list (`Store<PageKey,List<Loan>>`, offset/limit ≙ Fineract paging) drilling into a loan 360° (schedule / transactions / charges / guarantors / collateral / documents), with a **complete lifecycle command surface** — approve, reject, withdraw, disburse, undo-approval/disbursal, repayment, prepay, waive-interest, write-off, foreclose, reschedule, add/pay/waive charge, recalculate schedule. Each control is VISIBLE/enabled per the user's `{ACTION}_LOAN` permission **and** the loan's lifecycle state; a maker lacking an action sees it **disabled-with-reason** (operationally meaningful to see). Mutations queue to the outbox exactly-once; rejected commands route to `needs-attention-inbox`, never silently dropped. `requires_permission: [READ_LOAN]`.

### State: `loading` — list/detail shimmer
Header + search stay; loan rows (or the 360 detail) render as `shimmer-skeleton`; last cached content preserved underneath.

### State: `empty` — no loans
Illustration + empty message + a "New loan application" CTA (`empty_new_loan_cta`, only with CREATE_LOAN → `loan-application-wizard`).

### State: `action-disabled` — permission/stage mismatch
A maker (or a user lacking the specific action) sees the workflow control **disabled** with a reason chip ("Requires APPROVE_LOAN — ask your supervisor"). Disabled-not-hidden — the stage is meaningful to see (`button-primary-disabled` tonal fill).

### State: `schedule-preview` — live amortised preview
During an application/reschedule, the live repayment schedule preview (installments, principal/interest/fees split, total cost) recomputed via `calculateLoanSchedule` on every field change (debounced).

### State: `submitting` — queued command
A lifecycle/servicing command was queued through the outbox (durable idempotency key) — the control spins and the row shows a "Queued" / "Submitted for approval" chip; not optimistically applied until SUBMITTED (or approved under maker-checker).

### State: `error` — fetch/command failed
Server error shown verbatim + Retry; a rejected command routes to `needs-attention-inbox`, never silently dropped; last cached loan stays usable.

## Accessibility & Density Notes

- Actions are disabled-with-reason (not hidden) when the stage is meaningful — the reason chip names the missing permission for the operator.
- Destructive delinquency actions (write-off / foreclose) are `variant: destructive` + confirm + maker-checker aware.
- Queued/submitting rows carry a chip so the operator sees non-optimistic pending state.
- Rejected commands are surfaced in `needs-attention-inbox`, never silently dropped.
- All money/PAR figures in Roboto Mono for aligned portfolio scanning.
