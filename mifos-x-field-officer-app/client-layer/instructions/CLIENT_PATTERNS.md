## Architecture Overview

The client layer uses a **two-sealed-type pipeline** that separates network concerns from UI concerns. Data flows through two distinct boundaries, each represented by its own sealed type:

```
HTTP Response
    |
    v  (ResultSuspendConverterFactory -- automatic for Ktorfit)
NetworkResult<T, NetworkError>          <-- Network boundary
    |
    v  (ResultExtensions.toDataState() -- in repository)
DataState<T>                            <-- UI boundary
    |
    v  (ViewModel StateFlow)
Compose UI
```

### Why Two Sealed Types

| Boundary | Type | Responsibility |
|----------|------|----------------|
| Network | `NetworkResult<T, NetworkError>` | Classifies HTTP outcomes (status codes, timeouts, serialization failures) into typed errors. Services return this. |
| UI | `DataState<T>` | Represents UI display states (loading, success, pending refresh, error with cached data, offline). ViewModels and Compose observe this. |

The repository sits between the two boundaries. Its only job is to call `toDataState()` on the `NetworkResult` and then `.map {}` the DTO to a domain model. No try-catch, no manual error mapping.

> **Note on exemplar patterns**: The mobile-wallet exemplar uses an older pattern where services return raw types (`suspend fun ...(): T` or `Flow<T>`) and repositories use manual `try-catch` with `withContext(ioDispatcher)`. The `toDataState()` pipeline described here is the **recommended pattern** for new projects using the kmp-project-template foundation classes.

## DataState Pattern

### Definition (All 5 States)

```kotlin
sealed class DataState<out T> {
    abstract val data: T?

    data object Loading : DataState<Nothing>() {
        override val data: Nothing? = null
    }

    data class Success<T>(override val data: T) : DataState<T>()

    data class Pending<T>(override val data: T) : DataState<T>()

    data class Error<T>(
        val error: Throwable,
        override val data: T? = null,
    ) : DataState<T>()

    data class NoNetwork<T>(override val data: T? = null) : DataState<T>()
}
```

### State Descriptions

| State | When Used | `data` Field | Typical UI |
|-------|-----------|-------------|------------|
| `Loading` | Initial fetch, no data yet | `null` | Shimmer / spinner |
| `Success<T>` | Data fetched successfully | Non-null `T` | Render content |
| `Pending<T>` | Refreshing with stale data shown (optimistic updates) | Stale `T` | Content + refresh indicator |
| `Error<T>` | Request failed, may have cached data | Nullable (cached `T` or `null`) | Error banner, optional stale content |
| `NoNetwork<T>` | Device offline, may have cached data | Nullable (cached `T` or `null`) | Offline banner, optional stale content |

### DataState Extensions

There are two sets of extensions in the foundation:

**1. DataState.kt (core-base/common)** -- generic Flow conversion:

```kotlin
// Convert any Flow<T> into a Flow<DataState<T>> with automatic Loading/Success/Error
// Emits Loading on start, wraps values in Success, catches errors as Error
fun <T> Flow<T>.asDataStateFlow(): Flow<DataState<T>> =
    map<T, DataState<T>> { DataState.Success(it) }
        .onStart { emit(DataState.Loading) }
        .catch { emit(DataState.Error(it, null)) }
```

**2. ResultExtensions.kt (core/data)** -- NetworkResult-aware conversion:

```kotlin
// Convert Flow<NetworkResult> into Flow<DataState> with Loading emission
fun <D> Flow<NetworkResult<D, *>>.asDataStateFlow(): Flow<DataState<D>> =
    map { it.toDataState() }
        .onStart { emit(DataState.Loading) }

// Transform the success data without changing the state type
fun <T, R> DataState<T>.map(transform: (T) -> R): DataState<R>
```

The mobile-wallet exemplar uses `asDataStateFlow()` from `DataState.kt` (the generic version) because its services return raw `Flow<T>` types, not `Flow<NetworkResult>`. When using the `toDataState()` pipeline, use the `ResultExtensions.kt` version.

### Usage in ViewModel

```kotlin
class {Feature}ViewModel(
    private val repository: {Feature}Repository,
) : ViewModel() {

    private val _state = MutableStateFlow({Feature}State())
    val state: StateFlow<{Feature}State> = _state.asStateFlow()

    fun load{Feature}() {
        viewModelScope.launch {
            _state.update { it.copy(isLoading = true) }

            when (val result = repository.get{Feature}ById(id)) {
                is DataState.Loading -> {
                    _state.update { it.copy(isLoading = true) }
                }
                is DataState.Success -> {
                    _state.update {
                        it.copy(isLoading = false, item = result.data)
                    }
                }
                is DataState.Pending -> {
                    _state.update {
                        it.copy(isLoading = true, item = result.data)
                    }
                }
                is DataState.Error -> {
                    _state.update {
                        it.copy(
                            isLoading = false,
                            error = result.error.message,
                            item = result.data, // may have cached data
                        )
                    }
                }
                is DataState.NoNetwork -> {
                    _state.update {
                        it.copy(
                            isLoading = false,
                            isOffline = true,
                            item = result.data, // may have cached data
                        )
                    }
                }
            }
        }
    }
}
```

## Service Interface Pattern

The client layer supports two service modes. Both return `NetworkResult<T, NetworkError>` so that repositories use the same `toDataState()` conversion regardless of the backend.

### Mode 1: REST -- `{Feature}Api` (Ktorfit)

For REST endpoints, define a Ktorfit interface. The implementation is auto-generated by KSP at compile time. The `ResultSuspendConverterFactory` wraps every HTTP response into `NetworkResult` automatically, so methods never throw exceptions.

**Location**: `core/network/src/commonMain/kotlin/{package}/core/network/service/{feature}/{Feature}Api.kt`

```kotlin
package {appPackage}.core.network.service.{feature}

import de.jensklingenberg.ktorfit.http.*
import {appPackage}.core.network.model.{Feature}Dto
import {appPackage}.core.network.model.Create{Feature}Request
import {appPackage}.core.network.model.Update{Feature}Request
import template.core.base.network.NetworkError
import template.core.base.network.NetworkResult

/**
 * {Feature} API -- Ktorfit interface (REST endpoints).
 *
 * Return type convention:
 * - All methods return NetworkResult<T, NetworkError>
 * - ResultSuspendConverterFactory auto-wraps HTTP responses
 * - Methods never throw exceptions -- errors arrive as NetworkResult.Error
 */
interface {Feature}Api {

    @GET("{endpoint}")
    suspend fun get{Feature}s(): NetworkResult<List<{Feature}Dto>, NetworkError>

    @GET("{endpoint}/{id}")
    suspend fun get{Feature}ById(
        @Path("id") id: String,
    ): NetworkResult<{Feature}Dto, NetworkError>

    @GET("{endpoint}")
    suspend fun get{Feature}sPaginated(
        @Query("limit") limit: Int = 20,
        @Query("offset") offset: Int = 0,
    ): NetworkResult<{Feature}PageResponse, NetworkError>

    @POST("{endpoint}")
    suspend fun create{Feature}(
        @Body request: Create{Feature}Request,
    ): NetworkResult<{Feature}Dto, NetworkError>

    @PUT("{endpoint}/{id}")
    suspend fun update{Feature}(
        @Path("id") id: String,
        @Body request: Update{Feature}Request,
    ): NetworkResult<{Feature}Dto, NetworkError>

    @DELETE("{endpoint}/{id}")
    suspend fun delete{Feature}(
        @Path("id") id: String,
    ): NetworkResult<Unit, NetworkError>
}
```

### Mode 2: Supabase -- `{Feature}Service` + `{Feature}ServiceImpl`

For Supabase backends, define a manual interface and implementation. The implementation wraps Supabase SDK calls in `NetworkResult` explicitly. Both the interface and impl live in the same package.

**Location**: `core/network/src/commonMain/kotlin/{package}/core/network/service/{feature}/`

```kotlin
// Interface
interface {Feature}Service {
    suspend fun get{Feature}sByCategory(
        categoryId: String,
        limit: Int,
        offset: Int,
    ): NetworkResult<List<{Feature}Dto>, NetworkError>

    suspend fun get{Feature}ById(id: String): NetworkResult<{Feature}Dto, NetworkError>

    suspend fun create{Feature}(
        request: Create{Feature}Request,
    ): NetworkResult<{Feature}Dto, NetworkError>
}

// Implementation
class {Feature}ServiceImpl(
    private val client: SupabaseClient,
) : {Feature}Service {

    override suspend fun get{Feature}sByCategory(
        categoryId: String,
        limit: Int,
        offset: Int,
    ): NetworkResult<List<{Feature}Dto>, NetworkError> {
        return try {
            val params = buildJsonObject {
                put("p_category_id", categoryId)
                put("p_limit", limit)
                put("p_offset", offset)
            }
            val result = client.postgrest
                .rpc("get_{feature}s_by_category", params)
                .decodeList<{Feature}Dto>()
            NetworkResult.Success(result)
        } catch (e: Exception) {
            NetworkResult.Error(e.toNetworkError())
        }
    }

    override suspend fun get{Feature}ById(
        id: String,
    ): NetworkResult<{Feature}Dto, NetworkError> {
        return try {
            val result = client.postgrest
                .from("{feature}s")
                .select { filter { eq("id", id) } }
                .decodeSingle<{Feature}Dto>()
            NetworkResult.Success(result)
        } catch (e: Exception) {
            NetworkResult.Error(e.toNetworkError())
        }
    }

    override suspend fun create{Feature}(
        request: Create{Feature}Request,
    ): NetworkResult<{Feature}Dto, NetworkError> {
        return try {
            val result = client.postgrest
                .from("{feature}s")
                .insert(request) { select() }
                .decodeSingle<{Feature}Dto>()
            NetworkResult.Success(result)
        } catch (e: Exception) {
            NetworkResult.Error(e.toNetworkError())
        }
    }
}
```

### Naming Convention

| Suffix | Backend | Implementation | Example |
|--------|---------|----------------|---------|
| `{Feature}Api` | REST / Ktorfit | Auto-generated by KSP | `MovieApi`, `UserApi` |
| `{Feature}Service` + `{Feature}ServiceImpl` | Supabase | Manual interface + impl | `MovieService` / `MovieServiceImpl` |

Both return `NetworkResult<T, NetworkError>`. The repository does not know which backend it talks to.

### Key Rules

| Annotation | Usage | Return Type |
|------------|-------|-------------|
| `@GET` | Read operations | `suspend fun ...(): NetworkResult<T, NetworkError>` |
| `@POST` | Create operations | `suspend fun ...(): NetworkResult<T, NetworkError>` |
| `@PUT` | Full update operations | `suspend fun ...(): NetworkResult<T, NetworkError>` |
| `@PATCH` | Partial update operations | `suspend fun ...(): NetworkResult<T, NetworkError>` |
| `@DELETE` | Delete operations | `suspend fun ...(): NetworkResult<Unit, NetworkError>` |
| `@Path` | URL path variable | N/A |
| `@Query` | Query parameter | N/A |
| `@Body` | Request body | N/A |

Never use `Flow<T>` as a return type on a Ktorfit Api interface. Ktorfit endpoints are one-shot HTTP calls. If you need reactive streams (e.g., Supabase Realtime), use a `{Feature}Service` interface with Flow return types instead.

## Repository Pattern

### Location

```
core/data/src/commonMain/kotlin/{package}/core/data/repository/{Feature}Repository.kt
core/data/src/commonMain/kotlin/{package}/core/data/repositoryImpl/{Feature}RepositoryImpl.kt
```

### Repository Interface

```kotlin
package {appPackage}.core.data.repository

import {appPackage}.core.model.{Feature}
import template.core.base.common.DataState
import kotlinx.coroutines.flow.Flow

interface {Feature}Repository {

    // One-shot operations (most common)
    suspend fun get{Feature}s(): DataState<List<{Feature}>>
    suspend fun get{Feature}ById(id: String): DataState<{Feature}>
    suspend fun create{Feature}(request: Create{Feature}Request): DataState<{Feature}>
    suspend fun update{Feature}(id: String, request: Update{Feature}Request): DataState<{Feature}>
    suspend fun delete{Feature}(id: String): DataState<Unit>

    // Flow-based (for real-time or observe patterns)
    fun observe{Feature}s(): Flow<DataState<List<{Feature}>>>
}
```

### Repository Implementation -- The Clean Pattern

The repository bridges `NetworkResult` to `DataState` using `ResultExtensions.toDataState()`. No try-catch blocks. No manual error mapping. The conversion is a single function call.

```kotlin
package {appPackage}.core.data.repositoryImpl

import {appPackage}.core.data.mapper.to{Feature}
import {appPackage}.core.data.mapper.to{Feature}List
import {appPackage}.core.data.util.toDataState
import {appPackage}.core.model.{Feature}
import {appPackage}.core.network.service.{feature}.{Feature}Api
import template.core.base.common.DataState

class {Feature}RepositoryImpl(
    private val api: {Feature}Api,
) : {Feature}Repository {

    override suspend fun get{Feature}s(): DataState<List<{Feature}>> {
        return api.get{Feature}s().toDataState().map { dtos ->
            dtos.to{Feature}List()
        }
    }

    override suspend fun get{Feature}ById(id: String): DataState<{Feature}> {
        return api.get{Feature}ById(id).toDataState().map { dto ->
            dto.to{Feature}()
        }
    }

    override suspend fun create{Feature}(
        request: Create{Feature}Request,
    ): DataState<{Feature}> {
        return api.create{Feature}(request).toDataState().map { dto ->
            dto.to{Feature}()
        }
    }

    override suspend fun update{Feature}(
        id: String,
        request: Update{Feature}Request,
    ): DataState<{Feature}> {
        return api.update{Feature}(id, request).toDataState().map { dto ->
            dto.to{Feature}()
        }
    }

    override suspend fun delete{Feature}(id: String): DataState<Unit> {
        return api.delete{Feature}(id).toDataState()
    }
}
```

### ResultExtensions Bridge Functions

These extension functions live in `core/data/util/ResultExtensions.kt` and handle the `NetworkResult` to `DataState` conversion:

```kotlin
// Basic conversion -- maps NetworkResult to DataState
fun <D> NetworkResult<D, *>.toDataState(): DataState<D>

// Conversion with existing cached data -- on error, returns Error with data attached
fun <D> NetworkResult<D, *>.toDataState(existingData: D?): DataState<D>

// Smart conversion -- maps REQUEST_TIMEOUT to DataState.NoNetwork instead of Error
fun <D> NetworkResult<D, *>.toDataStateWithMapping(): DataState<D>

// Smart conversion with existing data preserved
fun <D> NetworkResult<D, *>.toDataStateWithMapping(existingData: D?): DataState<D>

// Convert a Flow<NetworkResult> to Flow<DataState> with Loading emission
fun <D> Flow<NetworkResult<D, *>>.asDataStateFlow(): Flow<DataState<D>>
```

**Conversion rules**:

| NetworkResult | DataState |
|---------------|-----------|
| `NetworkResult.Success(data)` | `DataState.Success(data)` |
| `NetworkResult.Error(NetworkError.REQUEST_TIMEOUT)` | `DataState.NoNetwork(existingData)` (via `toDataStateWithMapping()`) |
| `NetworkResult.Error(anyOtherError)` | `DataState.Error(throwable, existingData)` |

### Supabase Repository Implementation

When the backend is Supabase, the repository injects a `{Feature}Service` instead of a `{Feature}Api`. The pattern is identical because both return `NetworkResult`:

```kotlin
class {Feature}RepositoryImpl(
    private val service: {Feature}Service,
) : {Feature}Repository {

    override suspend fun get{Feature}s(): DataState<List<{Feature}>> =
        service.get{Feature}sByCategory(categoryId, limit, offset)
            .toDataState()
            .map { dtos -> dtos.to{Feature}List() }
}
```

## UseCase Pattern

UseCases encapsulate **business logic that spans multiple repositories** or requires orchestration beyond a single repository call. They sit between ViewModels and Repositories, keeping ViewModels thin and business rules testable in isolation.

### When to Use a UseCase

| Scenario | Use UseCase? | Reason |
|----------|:---:|--------|
| Single repository call with no extra logic | No | ViewModel calls repository directly |
| Combining data from 2+ repositories | **Yes** | Orchestration logic belongs in UseCase |
| Business validation before/after API call | **Yes** | Validation rules are domain logic |
| Multi-step workflows (login, checkout) | **Yes** | Sequencing and error handling across steps |
| Paged data with custom PagingSource | **Yes** | Pager configuration is domain-level |
| Simple CRUD pass-through | No | Adds unnecessary indirection |

### File Location

```
core/domain/src/commonMain/kotlin/{package}/core/domain/usecase/{feature}/{UseCase}UseCase.kt
```

### Standard UseCase Template

UseCases use `operator fun invoke(...)` so they can be called like functions from ViewModels.

```kotlin
package {appPackage}.core.domain.usecase.{feature}

import {appPackage}.core.data.repository.{Feature}Repository
import template.core.base.common.DataState
import kotlinx.coroutines.CoroutineDispatcher
import kotlinx.coroutines.withContext

/**
 * {Action}{Feature}UseCase
 *
 * {Description of what this use case does and why it exists as a UseCase
 * rather than a direct repository call.}
 */
class {Action}{Feature}UseCase(
    private val {feature}Repository: {Feature}Repository,
    private val ioDispatcher: CoroutineDispatcher,
) {
    /**
     * @param {params} {Description}
     * @return DataState with {result description}
     */
    suspend operator fun invoke({params}): DataState<{Result}> {
        return withContext(ioDispatcher) {
            {feature}Repository.{method}({params})
        }
    }
}
```

### Concrete Example: LoginUseCase (Multi-Repository Orchestration)

From the mobile-wallet exemplar -- combines authentication, client lookup, and preference storage:

```kotlin
class LoginUseCase(
    private val repository: AuthenticationRepository,
    private val clientRepository: ClientRepository,
    private val userPreferencesRepository: UserPreferencesRepository,
    private val ioDispatcher: CoroutineDispatcher,
) {
    suspend operator fun invoke(
        username: String,
        password: String,
    ): DataState<UserInfo> {
        val result = withContext(ioDispatcher) {
            repository.authenticate(username, password)
        }
        return when (result) {
            is DataState.Success -> updateUserInfo(result.data)
            is DataState.Error -> DataState.Error(Exception("Invalid credentials"))
            else -> result
        }
    }

    private suspend fun updateUserInfo(user: User): DataState<UserInfo> {
        return withContext(ioDispatcher) {
            val client = clientRepository.getClientDetails(user.clientId)
            userPreferencesRepository.saveUserInfo(user, client)
            DataState.Success(UserInfo(user, client))
        }
    }
}
```

### Pagination UseCase Template

For paged data, the UseCase configures a `Pager` and returns `Flow<PagingData<T>>`. The UseCase does **not** use `suspend` because it returns a cold Flow.

```kotlin
package {appPackage}.core.domain.usecase.{feature}

import androidx.paging.Pager
import androidx.paging.PagingConfig
import androidx.paging.PagingData
import {appPackage}.core.data.repository.{Feature}Repository
import {appPackage}.core.data.paging.{Feature}PagingSource
import {appPackage}.core.model.{Feature}
import kotlinx.coroutines.flow.Flow

/**
 * GetPaged{Feature}sUseCase
 *
 * Provides paginated {feature} data using Paging 3.
 * Configures page size and prefetch distance for optimal scrolling.
 */
class GetPaged{Feature}sUseCase(
    private val {feature}Repository: {Feature}Repository,
) {
    operator fun invoke(): Flow<PagingData<{Feature}>> {
        return Pager(
            config = PagingConfig(
                pageSize = PAGE_SIZE,
                prefetchDistance = PREFETCH_DISTANCE,
                enablePlaceholders = false,
            ),
            pagingSourceFactory = {
                {Feature}PagingSource({feature}Repository)
            },
        ).flow
    }

    companion object {
        private const val PAGE_SIZE = 20
        private const val PREFETCH_DISTANCE = 5
    }
}
```

### UseCase in ViewModel

```kotlin
class {Feature}ViewModel(
    private val get{Feature}UseCase: Get{Feature}UseCase,
    private val getPaged{Feature}sUseCase: GetPaged{Feature}sUseCase,
) : ViewModel() {

    // Standard UseCase call
    fun load{Feature}(id: String) {
        viewModelScope.launch {
            _state.update { it.copy(isLoading = true) }
            when (val result = get{Feature}UseCase(id)) {
                is DataState.Success -> _state.update {
                    it.copy(isLoading = false, item = result.data)
                }
                is DataState.Error -> _state.update {
                    it.copy(isLoading = false, error = result.error.message)
                }
                else -> { /* handle other states */ }
            }
        }
    }

    // Pagination UseCase -- exposed as Flow
    val pagedItems: Flow<PagingData<{Feature}>> =
        getPaged{Feature}sUseCase()
            .cachedIn(viewModelScope)
}
```

### UseCase DI Registration

```kotlin
// core/domain/di/UseCaseModule.kt
val useCaseModule = module {
    factory { LoginUseCase(get(), get(), get(), get()) }
```

> **Note**: UseCases are registered with `factory` (not `single`) because they are
> lightweight and should not hold shared state. Each injection site gets a fresh instance.

## NetworkResult-to-DataState Bridge

The bridge between `NetworkResult` and `DataState` lives in `ResultExtensions.kt`.
These extension functions are part of the foundation and are never regenerated.

### File Location

```
core/data/src/commonMain/kotlin/{package}/core/data/util/ResultExtensions.kt
```

### Core Bridge Functions

```kotlin
/**
 * Convert NetworkError to a Throwable with HTTP status code context.
 */
fun NetworkError.toThrowable(): Throwable = when (this) {
    NetworkError.BAD_REQUEST -> RemoteException("Bad Request", 400)
    NetworkError.UNAUTHORIZED -> RemoteException("Unauthorized", 401)
    NetworkError.NOT_FOUND -> RemoteException("Not Found", 404)
    NetworkError.REQUEST_TIMEOUT -> RemoteException("Request Timeout", 408)
    NetworkError.TOO_MANY_REQUESTS -> RemoteException("Too Many Requests", 429)
    NetworkError.SERVER -> RemoteException("Server Error", 500)
    NetworkError.SERIALIZATION -> RemoteException("Serialization Error", 0)
    NetworkError.UNKNOWN -> RemoteException("Unknown Error", -1)
}

/**
 * Convert a single NetworkResult into DataState.
 */
fun <D> NetworkResult<D, *>.toDataState(): DataState<D> = when (this) {
    is NetworkResult.Success -> DataState.Success(data)
    is NetworkResult.Error -> DataState.Error(error.toThrowable())
}

/**
 * Convert a Flow of NetworkResult into a Flow of DataState.
 * Emits Loading on start, catches unexpected errors.
 */
fun <D> Flow<NetworkResult<D, *>>.asDataStateFlow(): Flow<DataState<D>> =
    map { it.toDataState() }
        .onStart { emit(DataState.Loading) }
        .catch { emit(DataState.Error(it)) }
```

### DataState Utility Extensions

Convenience properties for checking and extracting DataState values in ViewModels:

```kotlin
/** Check if DataState is a successful state */
val <T> DataState<T>.isSuccess: Boolean
    get() = this is DataState.Success

/** Check if DataState is an error state */
val <T> DataState<T>.isError: Boolean
    get() = this is DataState.Error

/** Get the Throwable if DataState is in error state, null otherwise */
val <T> DataState<T>.errorOrNull: Throwable?
    get() = (this as? DataState.Error)?.error
```

```kotlin
// Primary pattern: NetworkResult -> DataState via toDataState()

        api.getMovies()

}
```

## DTO Patterns

### Location
`core/network/src/commonMain/kotlin/{package}/core/network/model/`

### Response DTO

```kotlin
@Serializable
data class {Feature}Dto(
    val id: String? = null,
    val name: String? = null,
    val status: String? = null,
    val createdAt: String? = null,
    // All fields nullable with defaults
)
```

### Request DTO

```kotlin
@Serializable
data class Create{Feature}Request(
    val name: String,
    val description: String? = null,
    // Required fields non-null, optional fields nullable
)

@Serializable
data class Update{Feature}Request(
    val name: String? = null,
    val description: String? = null,
    // All fields nullable (partial update)
)
```

### Page Response DTO

```kotlin
@Serializable
data class {Feature}PageResponse(
    val items: List<{Feature}Dto> = emptyList(),
    val total: Int = 0,
    val page: Int = 0,
    val pageSize: Int = 20,
)
```

### DTO Rules

| Rule | Example |
|------|---------|
| Response fields nullable with defaults | `val name: String? = null` |
| Request required fields non-null | `val name: String` |
| Always add `@Serializable` | For kotlinx.serialization JSON parsing |
| DTOs live in core/network/model | Never in core/model (that is domain) |
| Use `@SerialName` for API field mapping | `@SerialName("created_at") val createdAt: String?` |

## Mapper Pattern

### Location
`core/data/src/commonMain/kotlin/{package}/core/data/mapper/{Feature}Mapper.kt`

> **Note**: Mappers live in the `core/data` module (not `core/network`) because they bridge between the network layer DTOs and the domain models. This matches the reference exemplar (mobile-wallet) where all mappers reside in `core/data/mapper/`.

### Template

```kotlin
package {appPackage}.core.data.mapper

import {appPackage}.core.model.{Feature}
import {appPackage}.core.network.model.{Feature}Dto

fun {Feature}Dto.to{Feature}(): {Feature} {
    return {Feature}(
        id = id.orEmpty(),
        name = name.orEmpty(),
        status = status.orEmpty(),
    )
}

fun List<{Feature}Dto>.to{Feature}List(): List<{Feature}> {
    return map { it.to{Feature}() }
}

fun {Feature}.to{Feature}Dto(): {Feature}Dto {
    return {Feature}Dto(
        id = id,
        name = name,
        status = status,
    )
}
```

### Mapper Rules

| Rule | Reason |
|------|--------|
| Extension functions, not utility classes | Idiomatic Kotlin, discoverable |
| Handle nulls with `.orEmpty()` or defaults | DTOs are nullable, domain models should not be |
| One mapper file per feature | `{Feature}Mapper.kt` |
| Bidirectional when needed | DTO-to-Domain and Domain-to-DTO |

## DI Pattern

### Module Structure

The template project uses two Koin modules for client layer DI:

| Module | File | Registers |
|--------|------|-----------|
| `NetworkModule` | `core/network/di/NetworkModule.kt` | HttpClient, Ktorfit instance, all `{Feature}Api` and `{Feature}Service` singletons |
| `DataModule` | `core/data/di/RepositoryModule.kt` | All `{Feature}Repository` singletons |

### NetworkModule -- REST (Ktorfit Api)

```kotlin
// core/network/di/NetworkModule.kt
val networkModule = module {

    // HttpClient with plugins (logging, content negotiation, auth)
    single {
        HttpClient(CIO) {
            install(ContentNegotiation) { json(Json { ignoreUnknownKeys = true }) }
            install(Logging) { level = LogLevel.BODY }
            // ... other plugins
        }
    }

    // Ktorfit instance -- configured once with ResultSuspendConverterFactory
    single {
        Ktorfit.Builder()
            .baseUrl(BuildConfig.BASE_URL)
            .httpClient(get<HttpClient>())
            .converterFactories(ResultSuspendConverterFactory())
            .build()
    }

    // Api interfaces -- Ktorfit generates implementations at compile time via KSP
    single<{Feature}Api> { get<Ktorfit>().create<{Feature}Api>() }
    single<AnotherFeatureApi> { get<Ktorfit>().create<AnotherFeatureApi>() }
}
```

### NetworkModule -- Supabase (Service + ServiceImpl)

```kotlin
// core/network/di/NetworkModule.kt
val networkModule = module {

    // SupabaseClient
    single {
        createSupabaseClient(
            supabaseUrl = BuildConfig.SUPABASE_URL,
            supabaseKey = BuildConfig.SUPABASE_KEY,
        ) {
            install(Postgrest)
            install(Auth)
            install(Storage)
            install(Realtime)
        }
    }

    // Service interfaces -- manual implementations
    single<{Feature}Service> { {Feature}ServiceImpl(get()) }
    single<AnotherFeatureService> { AnotherFeatureServiceImpl(get()) }
}
```

### DataModule (RepositoryModule.kt)

```kotlin
// core/data/di/RepositoryModule.kt
val dataModule = module {

    // Repositories -- inject service/api from NetworkModule
    single<{Feature}Repository> { {Feature}RepositoryImpl(get()) }
    single<AnotherFeatureRepository> { AnotherFeatureRepositoryImpl(get()) }
}
```

### Mixed Backend DI (REST + Supabase)

When a project uses both REST and Supabase (e.g., Supabase for data, REST for third-party APIs):

```kotlin
val networkModule = module {
    // Ktorfit for REST
    single { Ktorfit.Builder().baseUrl(...).httpClient(get()).converterFactories(ResultSuspendConverterFactory()).build() }
    single<ThirdPartyApi> { get<Ktorfit>().create<ThirdPartyApi>() }

    // Supabase for data
    single { createSupabaseClient(...) { install(Postgrest); install(Auth) } }
    single<{Feature}Service> { {Feature}ServiceImpl(get()) }
}
```

## Error Handling

Error handling is automatic through the two-sealed-type pipeline. There is no manual try-catch in repositories when using the `toDataState()` pattern.

### How Errors Flow

```
HTTP 4xx/5xx
    |
    v  ResultSuspendConverterFactory
NetworkResult.Error(NetworkError.BAD_REQUEST)   -- classified at network boundary
    |
    v  toDataState()
DataState.Error(BadRequestException(...))       -- converted at repository boundary
    |
    v  ViewModel when() branch
UI error state                                  -- displayed at UI boundary
```

### NetworkError Classification

The `ResultSuspendConverterFactory` classifies HTTP responses into `NetworkError` variants:

| HTTP Response | NetworkError | DataState |
|---------------|-------------|-----------|
| 2xx | N/A (success) | `Success(body)` |
| 400 | `BAD_REQUEST` | `Error(...)` |
| 401 | `UNAUTHORIZED` | `Error(...)` |
| 404 | `NOT_FOUND` | `Error(...)` |
| 408 | `REQUEST_TIMEOUT` | `Error(...)` or `NoNetwork(...)` via `toDataStateWithMapping()` |
| 429 | `TOO_MANY_REQUESTS` | `Error(...)` |
| 5xx | `SERVER` | `Error(...)` |
| JSON parse failure | `SERIALIZATION` | `Error(...)` |
| Other / unknown | `UNKNOWN` | `Error(...)` |

### Error Handling in ViewModel

```kotlin
when (val result = repository.get{Feature}ById(id)) {
    is DataState.Success -> showContent(result.data)
    is DataState.Error -> showError(result.error.message)
    is DataState.NoNetwork -> showOfflineBanner(cachedData = result.data)
    is DataState.Loading -> showLoading()
    is DataState.Pending -> showContentWithRefreshIndicator(result.data)
}
```

For detailed error handling patterns (retry logic, user-friendly messages, field-level errors), see [ERROR_HANDLING.md](ERROR_HANDLING.md).

## Flow vs Suspend Guidelines

### Use Suspend When (Default)

| Scenario | Example |
|----------|---------|
| One-shot operations | `suspend fun getById(id: String): DataState<T>` |
| All CRUD operations | `suspend fun create(request): DataState<T>` |
| Single response needed | `suspend fun search(query): DataState<List<T>>` |
| Paged fetches | `suspend fun getPage(offset, limit): DataState<PageResponse>` |

Most repository methods should be `suspend`. Ktorfit endpoints are inherently one-shot HTTP calls.

### Use Flow When

| Scenario | Example |
|----------|---------|
| Real-time updates | Supabase Realtime `postgresChangeFlow` |
| Local database observation | Room `@Query fun observe(): Flow<List<T>>` |
| Combined local + remote | Emit cached, then fetch fresh |
| Continuous streams | WebSocket connections |

```kotlin
// Flow-based: observe local DB with remote refresh
fun observe{Feature}s(): Flow<DataState<List<{Feature}>>> = flow {
    emit(DataState.Loading)
    // Emit from local cache first
    val cached = localDao.getAll()
    if (cached.isNotEmpty()) {
        emit(DataState.Pending(cached.toDomainList()))
    }
    // Then fetch fresh from network
    val result = api.get{Feature}s().toDataState().map { it.toDomainList() }
    emit(result)
}.flowOn(ioDispatcher)
```

## Backend-Specific Patterns

The patterns above apply to **REST/Ktorfit** and **Supabase** backends. For other backend types, see:

### Backend Detection

```
Which backend does API.md specify?
+-- REST endpoints         --> Use Ktorfit Api patterns in THIS file
+-- Supabase tables/RPC   --> Use Supabase Service patterns in THIS file + SUPABASE_INDEX.md
+-- Mixed                  --> Use both, with Supabase for real-time features
```

### SDK Auto-Detection

The SDK is auto-detected based on `project_type` in PROJECT.md:

| project_type | SDK | Pattern Files |
|--------------|-----|---------------|
| `kmp` | supabase-kt 2.6.1 + Ktorfit 2.7.1 | [kotlin/](kotlin/) |
| `web` | @supabase/supabase-js 2.x | [javascript/](javascript/) |
| `backend-node` | @supabase/supabase-js 2.x | [javascript/](javascript/) |
| `backend-python` | supabase-py 2.x | [python/](python/) |

> Primary target: KMP (Kotlin Multiplatform). All platforms (Android, iOS, Desktop, Web) share the same Kotlin SDK.

### Pattern Comparison

| Aspect | REST/Ktorfit | Supabase |
|--------|--------------|----------|
| HTTP Client | Ktor + Ktorfit | Supabase SDK |
| Service Layer | `{Feature}Api` (Ktorfit auto-impl) | `{Feature}Service` + `{Feature}ServiceImpl` |
| Return Type | `NetworkResult<T, NetworkError>` (automatic) | `NetworkResult<T, NetworkError>` (manual wrap) |
| Repository Pattern | `api.method().toDataState().map {}` | `service.method().toDataState().map {}` |
| Real-time | WebSocket (manual) | Built-in (`postgresChangeFlow`) |
| Auth | Custom JWT | Supabase Auth (GoTrue) |
| DI | `get<Ktorfit>().create<Api>()` | `{Feature}ServiceImpl(get())` |
